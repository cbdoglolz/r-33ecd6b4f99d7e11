# 日常自动更新怎么工作

你继续使用原来的一个订阅地址。后续正常更新由 GitHub 运行，不需要开着自己的电脑。

## 每天自动做什么

北京时间 **10:17、22:17** 计划检查两次，流程如下：

```text
GitHub 到计划时间运行
  ↓
先运行回归测试，再恢复最近一次完整成功快照
  ↓
分别读取四份来源配置（clun 有指定的备用地址）
  ↓
检查格式、体积、路径、站点数量和来源是否齐全
  ↓
去除完全重复项，继承各来源解析器，整理名称和排列
  ↓
对照上次清单，沿用能明确对应的站点标识
  ↓
在临时目录生成并校验完整订阅、报告和清单
  ↓
有实际变化 → 保存完整快照 → 直接发布 Pages → 从线上读取验证
没有变化 → 核对线上版本；已发布则结束，尚未发布则补做发布
```

只读取来源配置，不下载影片，也不在构建时执行第三方解析器。它更新的是站点入口及其配置，站点里的影片列表仍由各站点接口提供。这不是每天抓取和保存影片的任务。

## 电视什么时候能看到更新

GitHub 会更新固定网址对应的文件，**不会直接推送到手机或电视**。播放器何时重新读取配置，取决于它的刷新方式和缓存。希望立即同步时，在播放器里手动刷新配置；通常不用重新输入地址。播放器若记住了上次选中的站点，还可能继续打开原站点。

订阅更新不会自动把多个站点的影片汇成统一分类，也不能保证源站的每个栏目都有数据。

## 入口是怎么整理的

- 四个来源显示为“一源、二源、三源、四源”，原来源 ID 仍保留在报告中。
- 名称统一标注来源和 API/CSP/JS/Python 类型；同源同名的保留项用短编号区分，不再把很长的 API 地址放在名称后。
- 按来源优先级、类型排列。同组里的老入口保留原有顺序，新入口追加到同组。
- 默认版本继续隐藏明确的工具入口，全量版本保留这些入口。不会因为接口响应慢就擅自删除站点。

这是显示与配置整理，不是基于实机播放结果的站点排名。

## 为什么这次要改站点标识逻辑

旧方法把参数指纹放进 key。上游只改请求头、解析器或参数时，key 也可能变化，播放器可能把它当成另一个站点。

现在 `manifest.json` 保存持久标识表，每次先读取上一次成功清单：

1. 配置完全对应，直接沿用旧 key。
2. 同来源、同原始 key 的保留项，如果 API/引擎或单个站点对应关系唯一，也沿用旧 key。
3. 同 key 下有多个相似实现且无法明确区分时，不按顺序猜配，报告新增或歧义；有标识冲突则阻止发布。
4. 消失的标识保留停用记录，防止复用到另一个站点；相同配置重新出现时可找回原标识。

第一次升级参考旧版清单，尽量沿用现有 key。保留 key 有助于收藏连续性，但播放器自己的收藏数据库和实机行为仍须单独验证。上游自行重用/改名 key 或含糊的重复项不能保证自动识别。

## 出问题时怎么处理

| 情况 | 自动处理 |
| --- | --- |
| 四源齐全、检查通过，内容有变化 | 保存快照，发布新文件，核对线上版本和 JSON |
| 内容没变，线上也是该版本 | 只保存检查记录，不提交快照、不重新发布 |
| 已存完整快照，但上次发布失败，线上还是旧版本 | 下次检查补做发布，不必等上游再变化 |
| 线上版本检查超时、503 或格式异常 | 工作流失败，保留当前 Pages，稍后重试；不猜测版本状态 |
| 任意一源失效、空站点或格式错误 | 不发布残缺结果，旧版继续使用 |
| 任意一源比上次减少超过 30% | 阻止自动发布，等待核查真实上游变化 |
| 上游 JAR/脚本可能不可用 | 不执行它们来冒充可播放测试；报告的配置通过不等于该依赖可运行 |

成功快照和成功发布是两个状态。`snapshots` 分支记录最近完整构建；最终是否上线，须看 `deploy` 工作及线上检查。自动重试会用线上 `report.json` 的版本与完整快照比较。

## 看哪里才能知道更新成功

打开仓库 **Actions → Refresh → 最近一次运行**：

- **build**：回归测试、来源抓取、配置检查是否通过。
- **snapshot**：本次是否需要保存新的完整快照；无变化时正常跳过。
- **deploy**：是否发布成功，并且线上文件已实际读回；无待发布内容时正常跳过。
- **check-运行ID** 附件：最近检查时间、来源数量、配置结果，以及是否需要发布，保留 30 天。发布是否成功仍以 deploy 的结果为准。
- **complete-运行ID** 附件：完整输出和原始来源缓存，保留 90 天。
- **failure-运行ID** 附件及失败步骤日志：上游或构建失败原因。

报告页区分三层状态：配置检查通过、站点首页/分类/搜索未逐站测试、电视播放未实测。网页上的时间是内容生成时间，不是最近定时检查时间；没有变化时它不会为了显得新鲜而更新。

`report.json` 的 `changes` 会逐项列出新增、调整和移除入口的 key、名称、类型、来源及改动字段，不只给一个总数。

## 手动更新、回滚与提醒

立即检查：Actions → Refresh → Run workflow，恢复字段留空。

回滚：从 `snapshots` 历史中找到一个已知成功版本，在 Run workflow 的 `restore_snapshot` 填完整提交 SHA。工作流校验这份完整快照后直接发布，不重新抓取上游。所有 public 文件及哈希一起恢复。手动恢复是明确的重新发布操作，允许恢复相同版本。

失败提醒使用 GitHub 的 Actions 通知，在个人 Settings → Notifications 设置；本项目没有擅自发送消息或创建告警 Issue。可以关注“最近成功运行是否超过 36 小时”。

GitHub 定时任务可能延迟或跳过。公开仓库长时间无活动可能停用 schedule，需要在 Actions 界面正常重新启用。不会靠无意义提交伪造活动，也不能承诺永久准点运行。

## 以后增加来源怎么做

在 `sources.json` 增加唯一 ID、显示标签、订阅地址及可选备用地址，补足测试后提交。ID 与站点标识有关，不要随意改动。新增来源必须和现有来源一样通过完整性检查，失败时不能发布缺少它的版本。

代码或来源配置变更会触发构建；生成文件保存在独立快照分支，不反复提交到 main 触发循环。运行权限按构建、快照保存和 Pages 发布分别限制。
